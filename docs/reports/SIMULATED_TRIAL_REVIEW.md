# 模拟试用审查报告

日期：2026-07-19

## 结论

在没有真实用户的情况下，本轮采用“假想用户 + 典型症状场景 + 本地规则验证”的方式做了一轮模拟试用。8 个核心场景全部通过，没有发现会阻断试用的 P0 安全问题。

最值得优先优化的问题不是规则准确性，而是反馈闭环：当前用户点击反馈后，数据只保存在用户自己的浏览器本机，项目维护者拿不到真实反馈。

## 测试方法

- 使用 `scripts/simulated-trial-review.js` 跑 8 个模拟试用场景。
- 使用 `node scripts/qa-all.js` 跑全量本地 QA。
- 不调用真实模型，不需要真实 API Key。
- 不收集用户原始输入。

## 优先优化清单

### P1：反馈收集闭环

当前反馈按钮会写入：

- `symptomMateFeedback`
- `symptomMateEvents`

但这两者都只在用户浏览器本机，维护者看不到。

建议下一步做一个低隐私成本的反馈出口：

- “复制反馈给作者”按钮
- 或跳转问卷
- 或代理端新增脱敏反馈接口

第一版只收：

- 是否看懂
- 是否信任建议
- 症状类别
- 风险等级
- 反馈原因选项

不要收用户原始症状文本。

### P1：口令验证可用性

口令验证依赖线上代理 `/api/config`。如果 Render 冷启动或网络波动，正确用户也可能被挡在门外。

建议：

- 错误文案改成“正在唤醒服务，请稍后重试”
- 增加一次自动重试
- 或提供“仅使用本地规则版”的备用入口

### P2：负向反馈颗粒度

当前“建议不符合”太粗，后续很难判断问题来源。

建议增加原因选项：

- 症状没识别准
- 风险判断太保守
- 风险判断太轻
- 科室推荐不合适
- 文案看不懂
- 页面流程卡住

### P2：给测试者任务卡

没有真实用户时，测试者容易随便点几下结束。建议给每个测试者固定任务：

1. 完成一次普通低风险自查。
2. 完成一次红旗自查。
3. 点一次反馈。
4. 查看隐私政策。
5. 回答“你下次身体不舒服会不会用它”。

### P2：RAG 暂缓扩大

如果线上 RAG 打开但知识库主要是项目文档，它对医疗理解帮助有限。

建议灰度期先关闭 RAG，或者只加入人工审核过的医学科普 Markdown，并写清来源和更新时间。

### P3：结果页首屏聚焦

结果页内容完整，但首次用户可能更关心“我现在该做什么”。

建议后续优化：

- 首屏更突出第一行动建议
- 把反馈按钮放在用户读完结果后
- 增加“我应该现在急诊吗”的明确句式

## 建议下一步

优先做“脱敏反馈出口”。在没有真实用户前，它是最能提高试用质量的功能。否则测试者即使点了反馈，你也看不到。
